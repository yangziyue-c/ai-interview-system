## 1. 模块概述与职责边界

### 1.1 模块定位

主后端与系统集成模块承担三类职责：对外提供统一接口供前端调用，对内编排业务流程（面试生命周期
与对话管理），向下集成出题、评估、知识库检索三类 AI 能力。它不生产算法与知识内容，负责把这些
能力组合成一个完整的、可运行的业务系统。

### 1.2 职责边界

| 范围 | 内容 |
| :--- | :--- |
| **本模块负责** | 系统架构与接口契约 · 数据模型 · 面试流程状态机与对话管理 · 适配层与降级机制 · 鉴权与权限 · 题库导入流水线 · 知识库服务集成适配 · 测试与仿真 · 部署运维 |
| **本模块集成** | 出题算法（P2）、评估打分与报告生成（P3）、知识库数据与向量检索服务（P5）、正式前端（P4） |
| **明确不做** | 出题策略内部决策、评分算法与锚点设计、题目内容生产、前端页面实现 |

### 1.3 与各模块的接口关系

- **与 P2（出题算法）**：本模块以数据库会话与岗位、轮次、历史问答为入参调用出题策略，
  取得下一题题干或"未命中"信号；未命中即触发降级链。算法内部如何选题不属本模块。
- **与 P3（评估服务）**：本模块通过 HTTP 调用其评估接口，并负责附加单题素材（按岗位与题干精确匹配题库中的得分点与校准锚点）与返回契约校验。
- **与 P4（前端）**：本模块提供 22 个 REST 接口、统一响应格式与鉴权体系；前端构建产物由本模块同端口挂载，无跨域问题。
- **与 P5（知识库）**：本模块负责数据导入落库、检索服务接入与集成适配（详见 5.5）。

## 2. 系统架构设计

### 2.1 分层架构

后端采用单一应用包 `backend/app/`（42 个 Python 文件，约 2800 行），按职责分为四层：

| 层次 | 模块 | 职责 |
| :--- | :--- | :--- |
| **接口层** | `api/`（9 个路由模块 + 依赖注入） | 参数校验、鉴权、响应装配；挂载于统一前缀 `/api/v1` |
| **业务层** | `core/`（异常、安全、状态机、评估权重） | 横切业务规则，与框架解耦 |
| **适配层** | `adapters/`（超时基类 + 出题适配器 + 评估适配器） | 隔离外部依赖，实现降级链 |
| **数据层** | `models/`、`schemas/`、`database.py` | ORM 模型、请求响应模型、异步引擎与会话管理 |

辅以 `config.py`（配置单点）、`redis_client.py`（缓存抽象）、`utils/response.py`（响应构造）。

### 2.2 技术选型论证

| 选型 | 理由 |
| :--- | :--- |
| **FastAPI（异步）** | 一次出题或评估涉及数秒至数十秒的外部调用，异步框架可在等待期间继续服务其他请求，避免线程阻塞；自带接口文档便于联调与验收 |
| **SQLAlchemy 2.0 异步 ORM** | 与异步框架同源；模型定义采用 `Mapped` 注解风格，类型清晰 |
| **SQLite 默认 + MySQL 可选** | 演示与开发零配置启动，生产可切换（详见 8.2） |
| **JWT 鉴权** | 无状态、便于横向扩展，契合前后端分离形态 |
| **适配器模式集成 AI 能力** | 各 AI 服务的可用性与响应时间不可控，必须以"可降级"的方式接入，而非直接耦合 |

### 2.3 目录组织与集成原则

项目按成员归属划分目录：`backend/app/`（本模块）、`backend/interviewer_new/`（P2）、
`backend/evaluator_new/`（P3）、`backend/rag/`（P5）、`frontend/`（P4）。

**集成原则**：成员成果只通过 import 或独立进程接入，不复制进集成层。各成员可在自己的
目录内独立迭代，集成层只依赖其对外契约，契约稳定则模块可并行演进。

### 2.4 配置管理

全部可调参数集中于 `config.py`，通过 `.env` 文件注入：数据库地址、缓存地址、外部服务地址、
三类超时预算、面试轮数上限、JWT 密钥与有效期、上传限制等。运行期调整行为无需改动代码。

## 3. 数据模型设计

### 3.1 七张业务表

| 表 | 承载内容 |
| :--- | :--- |
| `users` | 用户账号与画像（用户名、密码哈希、昵称、学号、目标岗位、头像地址） |
| `interviews` | 面试场次（所属用户、岗位、状态、当前轮次、起止时间） |
| `qa_records` | 逐轮问答记录（轮次、题干、作答、录音地址） |
| `reports` | 五维评估报告（总分与五个维度分、评语、优势、不足、建议） |
| `report_shares` | 报告分享链接（分享码、过期时间、访问计数） |
| `positions` | 岗位字典（编码、名称、描述、技术栈、考察重点、启用状态、排序） |
| `questions` | 结构化题库（19 列，见 3.2） |

### 3.2 关键设计考量

**题库结构化**：`questions` 表 19 列，除题干、岗位、题型、难度、阶段外，还包含基础与进阶得分点、
三级追问（L1/L2/L3）、降级策略、单题校准锚点、关联知识点、关键词、优先级，使出题与评估可直接
读取结构化依据，无需运行期文本解析。

**唯一性与幂等**：题库以 `(岗位, 原题编号)` 联合唯一约束，使导入天然幂等、可反复重跑；
报告表对面试编号唯一约束，在数据库层保证一场面试只产生一份报告。

**关系与级联**：问答记录、报告以外键关联面试并配置级联删除；索引集中在高频过滤字段。

**不定长数据**：报告的优势/不足/建议与岗位的技术栈/考察重点以 JSON 列存储，
在"条目数不固定"与"查询效率"间取得平衡。

**用户输入的边界**：头像地址仅接受本模块上传接口产出的站内路径，外部地址与路径穿越一律拒绝。
该字段随用户信息接口下发并被前端渲染，放开任意字符串等于允许用户互相注入。

### 3.3 受控词表单一事实源

题型（4 类）、难度（3 档）、面试阶段（3 个）三类枚举常量只在模型定义文件中声明一次，
查询接口的合法性校验与导入脚本的字段校验共用同一常量。

词表一旦调整，只需改动一处，接口校验与导入逻辑自动跟随，非法值会立刻报错而非静默返回空集，
避免了"题库数据改了名、查询接口查不到数据"这类难排查的隐性故障。

## 4. 核心业务流程设计

### 4.1 面试状态机

面试生命周期由独立的状态机模块管理（约 45 行），三个状态：待开始 → 进行中 → 已结束。

实现采用表驱动：以字典显式声明"每个状态允许转移到哪些状态"，终态映射为空集。
两个入口分别用于"转换"（校验并写入，非法即拒绝）与"断言"（要求当前必须处于某状态）。
状态列以字符串存储，合法性完全由代码层保证。

**设计理由**：相比数据库枚举类型，表驱动方案让"新增状态"只需修改一处映射，无需变更表结构；
非法转换统一返回 409 冲突，避免"已结束的面试又被追加问答"这类脏数据。

### 4.2 七轮对话闭环

一场标准面试为 7 轮 = 1 道开场题 + 6 轮动态追问（轮数上限可配置）。流程如下：

1. **开始面试**：校验岗位合法性，检查该用户无进行中的面试（否则拒绝），生成开场题并落库，状态转入进行中；
2. **提交答案**：保存作答 → 若未达轮数上限则调用出题策略生成追问 → 若已达上限则自动结束面试并生成报告；
3. **主动结束**：允许考生提前结束，直接生成报告。

追问的内容由 P2 出题算法决定（按考生回答质量分层深入或降级引导），本模块负责流程编排：
轮次推进、上限控制、状态流转、持久化与报告触发。

### 4.3 出题即落库的持久化方式

问答记录采用"出题即落库、作答再回填"：每次生成题目立刻写入记录（作答字段为空），
考生提交答案时回填该条记录。

这一方式下，任意时刻中断（关闭页面、网络中断、服务重启），数据都处于一致状态，
不存在"有答案却没有对应问题"的脏数据；恢复会话时可直接重建完整对话历史。

### 4.4 参数化配置

面试轮数、追问上限、各类超时预算、上传大小与格式白名单等均来自配置层，
前端可通过运行参数接口获取当前轮数（前端不硬编码），保证前后端对面试节奏的认知始终一致。

## 5. 系统集成设计

### 5.1 适配器模式

所有外部 AI 能力统一经适配层访问。适配层基类提供"带超时调用 + 失败降级"的通用能力，
各适配器负责自身协议的拼装与解析。业务层只依赖适配器的返回契约，不感知外部服务的实现与可用性。

### 5.2 五级数据源降级链

出题能力组织为五级数据源，自上而下逐级尝试，任一级失败自动落到下一级：

| 级 | 数据源 | 生效条件 | 超时预算 |
| :--: | :--- | :--- | :--- |
| 1 | 题库策略 | 岗位有题且策略命中，绝大多数场次走此级 | 无网络开销 |
| 2 | 知识库语义检索 | 第 1 级未命中，且服务健康探测通过 | 60 秒 |
| 3 | 外部出题服务 | 已配置服务地址且前两级未命中 | 15 秒 |
| 4 | 大模型直连 | 已配置接口密钥与地址 | 15 秒 |
| 5 | 内置兜底题库 | 以上全部未命中时生效 | 0 |

**机制**：每一级内部自行捕获异常并返回"未命中"信号，首个成功结果即返回。
因此单点故障不会中断面试：即使知识库与大模型全部不可用，考生仍能完成一场结构完整的面试。

### 5.3 超时预算分档

三类调用采用差异化超时，而非统一值：

| 档位 | 适用 | 设定依据 |
| :--- | :--- | :--- |
| 60 秒 | 知识库语义检索 | 含向量召回与重排精排，是本系统最慢的接口，必须给足余量 |
| 30 秒 | 评估服务 | 需对大模型输出做多维度判分，耗时高于通用调用但低于检索 |
| 15 秒 | 其余 HTTP / 大模型调用 | 常规外部调用上限 |

**为何不统一**：若把检索超时按常规接口设为个位数秒，会造成每一次检索都误判为"服务不可用"
而白白降级，降级链看似生效，实际第 2 级从未真正工作过。按各服务真实耗时画像分档，
才能区分"服务慢"与"服务不可用"。知识库服务在调用前做健康探测并缓存结果 120 秒，
探测超时仅 0.5 秒，避免 7 轮对话反复探测拖慢响应。

### 5.4 契约归一化与防御式校验

外部服务返回的数据一律视为不可信，在适配层完成归一化后才进入业务层：

- **评估结果校验**：要求六个分数字段齐全、均为数值型、且落在 0~100 合法区间，非数值与越界值无法通过这一校验；
  任一不符即整体回退到兜底实现，业务层直接取值而不做防御判断。宁可给出一份可用的兜底报告，
  也不把异常数据写进用户报告。
- **单题素材匹配**：为评估服务附加题目素材时，按岗位 + 题干双重精确匹配。
  不同岗位可能存在题干相同的题目，仅按题干匹配会把其他岗位的评分口径喂给评估模型，
  这比"取不到素材"更危险，因此匹配策略从设计上排除了这种可能。
- **岗位名映射**：知识库使用岗位全名作为检索维度，映射表中未登记的岗位跳过该级降级，
  而不是退化为全库检索（后者会返回跨岗位的无关题目）。

### 5.5 知识库服务的集成适配

知识库数据与向量检索服务由 P5 提供，本模块负责将其落地为可运行、可部署的服务，
共完成 13 处适配改动，按性质分为四类：

| 类别 | 典型改动 | 解决的问题 |
| :--- | :--- | :--- |
| **服务可用性** | 端口调整并统一纳入项目端口规划；补全跨域支持；查询异常改为返回空结果而非直接报错 | 使服务符合项目约定、可供前端与其他服务安全调用 |
| **首次部署可行性** | 解除离线模式限制（允许首次自动下载模型）；线程数改为按 CPU 核数自适应；支持路径与端口的环境变量覆盖 | 避免在无预置模型的机器上"一启动就失败"，并适配不同部署目录结构 |
| **故障可见性** | 路径探测失败时快速报错（而非静默创建空库）；启动时打印实际命中的路径与条目数 | 高质量数据静默加载失败是最难排查的故障，改为显式失败与显式确认 |
| **工程规范性** | 补充依赖清单（与主依赖隔离）；补全服务文档与对接说明；向量库目录改为纯 ASCII 命名 | 依赖体积隔离与跨环境可移植性 |

其中向量库目录命名一项最隐蔽：向量库底层组件无法打开含非 ASCII 字符的绝对路径，
且故障表现为"服务正常启动、检索永远无结果"，容易误判为数据损坏。该问题在数据构建侧
同样存在（用中文路径构建会产出缺失索引文件的坏库），因此已在构建与加载两侧同时加入改名与路径守卫。

**佐证**：本模块最初将检索超时设为 5 秒，实测单次检索（含精排）在 CPU 上需 20~30 秒，
意味着该级降级从未真正生效；修正为 60 秒后才真正进入出题链路。

## 6. 接口设计与契约规范

### 6.1 统一响应格式

全部接口返回统一结构：`{code, message, data}`，成功时 `code = 0`。
通过全局异常处理，任何异常都不会返回非统一格式的响应，前端只需实现一套解析逻辑。

### 6.2 异常与错误码体系

异常基类直接继承框架的 HTTP 异常，子类只需声明业务错误码与提示语，HTTP 状态码自动对应。
错误码分为六档：参数错误、未认证、无权限、资源不存在、状态冲突、服务端错误。

全局兜底分三层：业务异常按声明返回；参数校验失败统一压平为可读中文提示（而非框架原始的嵌套报错）；
未预期异常统一记录日志并返回标准结构。业务代码内部因此无需书写防御性捕获。

### 6.3 鉴权与越权防护

- **鉴权**：JWT（HS256）无状态令牌，有效期可配置（默认 24 小时）；令牌解析的四类失败情形统一转为未认证错误；
- **密码**：bcrypt 加盐哈希存储，校验失败返回否而不是抛出异常；
- **依赖注入**：以类型别名封装"当前用户"与"数据库会话"两个依赖，路由签名一行即可获取，避免重复样板代码；
- **越权防护**：所有涉及面试资源的操作，均以"资源编号 + 当前用户编号"双条件查询，
  非本人资源一律返回"不存在"（而非"无权限"），避免泄露资源存在性。
- **免登录边界**：报告分享接口是本模块唯一不校验令牌的业务接口，单独成模块挂载，
  使鉴权边界在目录结构上直接可见。分享码为 128 位随机串，不具备枚举可行性；
  链接过期与不存在返回同一提示，不泄露有效分享码集合。

### 6.4 接口清单

共 22 个 REST 接口，全部挂载于 `/api/v1`，除注册、登录与报告分享外均需携带令牌：

| 模块 | 接口数 | 主要能力 |
| :--- | :--: | :--- |
| 认证 | 4 | 注册（自动登录）、登录、获取当前用户、更新个人资料 |
| 岗位 | 1 | 岗位列表（仅返回已开放岗位） |
| 面试 | 5 | 开始面试、历史列表（可按岗位筛选）、详情（含全部问答）、提交答案并获取下一题、主动结束 |
| 报告 | 4 | 指定面试报告、最近一次改进建议、能力成长曲线（可按岗位筛选）、生成分享链接 |
| 题库 | 2 | 题库列表（多维过滤 + 关键词搜索 + 分页）、单题详情 |
| 知识库检索 | 1 | 语义检索透传（服务不可用时优雅返回"不可用"而非报错） |
| 上传 | 2 | 面试录音上传、头像上传（格式白名单 + 文件头校验 + 大小限制 + 按用户隔离存储） |
| 分享 | 1 | 凭分享码查看报告（唯一不校验令牌的业务接口） |
| 系统 | 2 | 健康检查、前端运行参数下发 |

**说明**：本模块未设计独立的"取下一题"接口，下一题随"提交答案"的响应一并返回，
使一次网络往返即可完成"交卷 + 取题"，减少面试过程中的等待与状态不一致风险。

## 7. 工程质量保障

### 7.1 自动化测试体系

**规模**：84 项测试用例（接口 40 项、出题策略 37 项、评估服务 7 项），全量运行约 10 秒，测试代码约 1500 行。

**隔离机制**（顺序敏感）：测试配置在导入应用之前注入环境变量：切换至独立测试数据库、
清空全部外部服务地址与大模型密钥。顺序至关重要，若晚于应用导入，配置此时已读入内存、隔离失效。
其中知识库服务地址也一并清空：该地址默认指向本机服务，若不隔离，"题库未命中应降级"的用例
会实际连上本机服务，服务未启动则等满探测超时，已启动则拿到真实数据，两种情况都会让断言失真。
测试会话开始时自动重建测试数据库，全程不触碰开发数据库。

**造数工厂**：共享的题目构造函数为各字段提供合理默认值，并对题目编号追加随机后缀，
绕开联合唯一约束，使测试可反复造数而不冲突。

### 7.2 流程仿真验证

除单元与接口测试外，提供面试流程仿真工具，用于在算法或数据变更后量化验证效果：

- **规模**：5 个岗位 × 每岗位 400 场（模拟"答得好"与"答不出"两类考生）= 2000 场；
- **判据**：① 兜底题库调用 0 次（说明题库覆盖充分）② 收尾题出现率 100%（说明面试结构完整）；
- **实现**：仿真直接调用出题决策函数并复用出题侧的查询投影，确保"仿真通过"的证据强度与真实运行一致。

该工具在算法换代时暴露出一个问题：V5 数据结构下旧的关键词匹配机制追问触达率仅约 66%，
仿真量化定位后，算法改为语义分流并达到 100%。

### 7.3 数据库并发处理

针对默认数据库的并发写入特性做两层保障：连接层设置线程与超时参数；并在每个连接建立时
自动启用写前日志模式与忙等超时（30 秒）。

**效果**：读操作不阻塞写操作，多场面试并发提交时等待锁释放而非直接报错，
规避了轻量数据库并发写入最常见的失败模式。该配置仅对轻量数据库生效，切换至 MySQL 时自动跳过。

## 8. 部署与运维方案

### 8.1 一键启动编排

提供单命令启动脚本（编排逻辑约 300 行，以脚本文件承载以避免命令行解释器的编码与换行兼容问题），
自动完成：定位运行环境 → 检测并按需安装依赖 → 生成配置文件 → 依次拉起各服务 → 输出访问指引。

**拉起顺序**经过刻意设计：先启动评估服务，再启动主服务（前台运行），随后是演示前端，
知识库检索服务排在最后。因其首次运行需下载数 GB 模型与依赖，若排在前面会让主服务启动时多等数分钟。

**就绪探测**：以标准库轮询主服务健康检查接口，上限 30 秒，同时监控子进程存活：
进程若已崩溃则立即返回，不必等满超时；端口被占用时给出明确指引而非谎报可用。

**优雅退出**：子进程的创建与等待均置于异常保护中，退出时按依赖顺序依次终止，超时未退则强制结束，
不残留占用端口的孤儿进程。

**依赖体积隔离**：知识库相关依赖（约 2.5 GB）与主依赖刻意分离为两个清单。主流程不依赖它们，
混入主清单会让每个新环境都强制下载数 GB；安装时优先选择 CPU 版深度学习运行时，
避免默认拉取体积更大的 GPU 版本。

### 8.2 双数据库切换

通过配置层屏蔽差异：切换数据库只需修改配置文件中的一行连接串。
轻量数据库专属的连接参数与并发配置由连接串前缀守卫，切换至 MySQL 时自动跳过，
同一套数据访问代码无需改动。

### 8.3 启动自愈与结构守卫

系统启动时自动执行一系列幂等的自愈动作：创建缺失的表、补充新增的可空列、
为历史报告回填缺失的维度分、对齐岗位字典（含将早期占位岗位幂等改名为正式岗位，历史数据不受影响）。

**表结构守卫**：题库表曾经历过含删列的字段重构，无法自动迁移。启动时比对实际列与期望列，
不一致则输出错误日志并附上可直接执行的修复命令。此处刻意采用"只告警不阻断"的策略：
旧数据库仍可启动（未命中的字段查询会自然降级），比直接启动失败更利于现场排查。

### 8.4 演示与内网穿透

系统支持通过内网穿透对外演示，评委或用户无需本地部署即可访问；一键启动完成后打印本机与局域网
两套访问地址及各自用途，降低演示门槛。

> 另有一套零依赖演示前端（约 1700 行，纯原生实现、无构建步骤、无第三方依赖）随一键启动自动就绪，
> 用于在正式前端交付前提供完整流程演示；正式前端由 P4 负责，构建产物由本模块同端口挂载。

## 9. 关键技术难点与解决方案

| # | 难点 | 解决方案 | 效果 |
| :--: | :--- | :--- | :--- |
| 1 | 外部 AI 服务不可控，任一环节故障即中断面试 | 适配器 + 五级降级链，逐级回退，末端为内置兜底 | 面试流程不中断 |
| 2 | 统一超时会让慢接口误判为不可用 | 按真实耗时分档设定超时（60/30/15 秒） | 知识库检索真正进入出题链路 |
| 3 | 数据静默加载失败（路径异常时创建空库） | 探测失败快速报错 + 启动打印命中路径与条目数 | 故障从"检索无结果"变为"启动即报错" |
| 4 | 向量库在非 ASCII 路径下无法加载，故障现象易误判 | 目录改纯 ASCII 命名 + 构建/加载两侧路径守卫 | 消除"服务正常但检索无结果" |
| 5 | 外部评分数据不可信，异常值污染用户报告 | 契约归一化：字段齐全性 + 数值合法性校验 | 异常数据不进入报告 |
| 6 | 并发提交时轻量数据库锁库报错 | 连接层自动启用写前日志 + 忙等超时 | 转为等待锁释放，不再直接失败 |
| 7 | 词表变更后静默查不到数据 | 题型/难度/阶段单一事实源，接口与脚本共用 | 改一处生效，非法值立即报错 |
| 8 | 新环境部署门槛高（依赖多、模型大） | 单命令编排：检测→安装→配置→拉起→探测→退出 | 无需配置即可演示 |
| 9 | 分享链接对外发送，接收方无账号，且链接可能被枚举试探 | 分享码独立成表、128 位随机、带有效期；不存在与已过期返回同一提示 | 报告可外发，分享码不可枚举 |
