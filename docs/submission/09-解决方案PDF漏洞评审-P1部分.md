# 《解决方案》PDF 漏洞评审与修改建议

> 评审对象：项目根目录 `解决方案.pdf`（123 页，2026-11 版）
> 评审范围：与当前代码、运行说明、提交材料的一致性，以及答辩时可能被追问的事实错误。
> 分级说明：
> - A 级：现场会被直接击穿，必须改。
> - B 级：事实不准确，可能被追问，建议改。
> - C 级：已如实披露的边界，可保留，作为评委提问的钩子。
> - D 级：决赛新增功能与 PDF 脱节，需要补写或准备口径。
>
> 页码为 PDF 页码（与页脚正文页码相差约 1 页），定位以章节号为准。

## 一、结论

PDF 的技术叙述整体扎实，第 6、7 章对引擎链路的描述与代码基本一致，第 12 章对不足的披露也足够诚实。问题集中在三处：

1. **评分验证声称完成了人工评分一致性验证，但实际没有人工标注集**，而且 6.4.4 自己写着「未完成真人专家校准前，合成分必须显示未校准」。这是全书最容易被击穿的矛盾。
2. **架构把 8002 评估服务写成了 8005 的一部分**，并称主后端、面试官服务、评估层都用 FastAPI。实际评估服务是 Flask 8002，面试官算法是主后端进程内的代码模块。运行说明与现场进程会直接暴露这一处。
3. **题库被反复描述为含「参考答案」或「优秀范例」**，实际 V5 的 18 个字段里没有这两项，只有基础得分点、进阶得分点与校准锚点。评委要求现场打开题库文件时会对不上。

下面逐条列出。

## 二、A 级：必须修改

### A1 人工评分一致性验证并不存在

位置：8.5「评分机制验证」、12.1.2「技术验证与测试完成」。

原文：

> 与人工评分的一致性验证：邀请具备面试经验的成员对若干样本进行人工打分，计算大模型评分与人工评分的相关系数，作为评估体系可信度的参考指标。
>
> 评估服务通过了一致性验证、校准有效性验证、与人工评分的一致性验证。

问题：当前没有人工标注集，也没有相关系数数据。可执行的只有两件事：同一答案重复评分的稳定性实验，以及按校准锚点构造三档答案的单调性实验。后者还是决赛阶段才写的脚本，尚未产出数据。更矛盾的是 6.4.4 写着「未完成真人专家校准前，合成分必须显示未校准」，与 8.5 的表述直接冲突。

建议改法：把 8.5 的三段改为两段，第三段降级为计划。

> 一致性验证：同一份问答记录重复调用评估服务，检查五维分数的波动范围。
>
> 校准有效性验证：按单题校准锚点构造优秀、合格、较差三档答案，检查分数是否严格单调。
>
> 与人工评分的一致性验证尚在规划中。人工标注集需要覆盖五个岗位与三档水平，样本量达到要求后再计算相关系数；在完成之前，报告中的合成分标注为「未校准」。

12.1.2 同步改为：「评估服务完成了一致性验证与校准有效性验证；与人工评分的一致性验证尚在规划中。」

答辩口径（如果来不及改）：被问到时直接说「人工标注集还没建，目前只能证明稳定与相对排序，绝对分校准是下一步」。评委对诚实边界的容忍度高于对夸大的容忍度。

### A2 评分口径混用：0 到 5 分与 0 到 100 分没有区分链路

位置：第 8 章开篇、8.1、6.4、12.1.1。

原文：

> 评分采用 0 到 5 分制，默认步进 0.05，最终总分由五个维度按岗位权重加权计算得出。

问题：这句话只对引擎链路成立。原链路 P3 评估服务（8002）的提示词明确要求 0 到 100 分，主后端 `reports` 表也存 0 到 100。引擎链路才是 1 到 5 分制乘 20 换算。PDF 把两条链路的评分口径合并成一条，评委会问「你们的报告到底是 0 到 5 还是 0 到 100」，而且 6.4 的 Qwen 客观线、原子断言、置信度合成分全部是引擎链路的实现，不是 8002 的。

建议改法：第 8 章开篇加一句链路区分。

> 评分有两套实现。原链路由独立评估服务按 0 到 100 分制给出五维分；引擎链路由 AI 对话层按 1 到 5 分制逐轮评分，再乘 20 换算为百分制。报告对外统一为 0 到 100，换算只在一处完成。

6.4 标题改为「AI 对话层引擎的评分模块」，并在开头注明「本节描述引擎链路；原链路的评估服务按题注入校准锚点，直接输出百分制五维分」。

答辩口径：两条链路的分数不可直接比较，成长曲线按链路筛选，这一点 PDF 8.4.2 已经写对，可以直接引用。

### A3 架构把 8002 评估服务写成了 8005 的一部分

位置：4.1、4.1.2、4.3.2、4.3.3、4.3.4、4.5.2。

原文：

> AI 对话与评估层运行于 8005 端口，负责题库、检索、追问、评分与多模态分析。
>
> 主后端、AI 面试官服务与 AI 对话与评估层（8005）均选择 FastAPI。
>
> 评估逻辑作为该服务层的一部分，与出题、追问、检索共享同一个进程和接口框架，不再单独维护一个轻量服务。

问题：实际进程与端口是：

| 端口 | 进程 | 框架 | 职责 |
| :--- | :--- | :--- | :--- |
| 8001 | 主后端 | FastAPI | 接口、状态机、集成、报告落库 |
| 8002 | P3 评估服务 | Flask | 原链路五维评分 |
| 8003 | RAG 检索 | FastAPI | 语义检索 |
| 8005 | AI 对话层引擎 | FastAPI | 引擎链路的出题、追问、评分、多模态 |
| 5273 | 演示前端 | 静态服务 | 演示入口 |

P2 的出题算法不是独立服务，是主后端进程内的代码模块（`interviewer_new/`）。PDF 的「面试官服务返回下一题」与「面试官服务选择 FastAPI」都不准确。

建议改法：4.1 的服务层拆成四条，按上表重写。4.1.2 的「主后端调用 AI 对话与评估层（8005）的评估接口」改为「原链路调用 8002 评估服务；引擎链路调用 8005 的 `/finish`」。4.3.2 改为「主后端与对话层使用 FastAPI；评估服务使用 Flask，独立进程部署」。4.3.4 的「不再单独维护一个轻量服务」删除。

答辩口径：如果 PDF 不改，现场被问「8002 是干什么的」时，直接按上表说明，不要顺着 PDF 的 8005 说法走。

### A4 题库没有「参考答案」与「优秀范例」

位置：5.2.1、5.2.2、6.3.1、7.1.6、7.2.2、6.8.10。

原文多处：

> 内容字段包括题目内容、基础得分点、进阶得分点、参考答案。
>
> 团队补充了完整的参考答案，平均长度从最初的几十字提升到 570 至 760 字。
>
> 提示词包含岗位信息、对话记录、评分标准、优秀范例与输出格式五部分。
>
> 题库中心让用户在面试练习之外，可以按知识点直接查阅题目与参考答案。

问题：V5 题库 JSON 的 18 个字段是：题目ID、所属岗位、题型分类、难度等级、面试阶段、核心关键词、考点优先级、题目内容、基础得分点、进阶得分点、L1基础追问、L2递进追问、L3拓展追问、降级策略、建议用时、适用题型基准、单题校准锚点、关联知识点。没有「参考答案」，也没有「优秀范例」。决赛阶段新增的示范作答是运行时按得分点生成并缓存的，不是题库预置内容。

建议改法：全文把「参考答案」替换为「基础得分点与进阶得分点」；需要强调完整作答时，写「系统按得分点生成的示范作答」。5.2.2 的「570 至 760 字」如果依据的是旧版数据，删除或改为当前得分点字段的实际长度统计。7.1.6 的「优秀范例」改为「单题校准锚点」。

答辩口径：可以主动说「题库刻意不存完整答案，只存可判分的得分点，避免考生背范文；示范作答在面试结束后按需生成」。这比声称有参考答案更站得住。

### A5 测试数字内部矛盾且已过时

位置：9.1.1、9.2.1、9.1.2。

答辩口径：如果 PDF 来不及改，现场只说「210 项」这一处，不要说 180。

位置：4.2、6.8、12.1.1。

原文：

> 前端完成了 14 个页面与 1 个设置组件的开发，支持移动端与电脑端的响应式布局。

## 三、B 级：建议修改

### B1 静态目录其实已经配置了 SPA fallback

位置：4.1.1。

原文：「路由采用 hash 模式，因为后端静态目录未配置 SPA fallback，history 模式下刷新子路径会返回 404。」

问题：`app/main.py` 的 `SPAStaticFiles` 已经实现未命中静态文件时回退 `index.html`，`/api` 前缀除外。PDF 的理由过时。

建议：改为「前端采用 hash 路由，避免不同部署环境下的路径回退差异」，或直接删掉理由。

### B2 评估服务并不下载录音做语音分析

位置：4.4.2、6.4。

原文：「评估服务从音频地址下载录音，调用语音分析提取语速、停顿等客观指标，作为表达能力的证据。」

问题：当前 P3 的 `_speech_details` 是按回答字数估的模拟值（`simulated: True`），不下载音频，代码注释明确说它是接入真实 ASR 前的占位。真实语速、停顿来自 ASR 接口返回的读数，随答案提交后落库，由主后端聚合进报告的「表达与表现分析」。

建议：改为「语音读数由转写接口产出，随答案提交落库；评估服务以文本评分为主，报告侧的语音展示由主后端聚合」。

### B3 三类上传并非都校验文件头

位置：9.4.3。

原文：「三类上传（头像、录音、简历）分别设白名单与体积上限，并在白名单之外校验文件头。」

问题：头像与简历校验文件头，录音只校验扩展名与大小。

建议：改为「头像与简历在扩展名之外校验文件头；录音按扩展名白名单与 20MB 上限限制」。

### B4 题库字段没有「原题 ID」

位置：6.3.1。

原文：「基础元数据包括题目 ID、原题 ID、所属岗位……」。

问题：题库 JSON 的字段是「题目ID」；「原题ID」是 RAG 向量库元数据里的键，两者不是同一份文件。

建议：删掉「原题 ID」，或注明「RAG 元数据以原题 ID 与题库主键对齐」。

### B5 摄像头是否参与评分，两处语气矛盾

位置：6.5.5 与 7.5.1、7.5.2。

原文：「即使接入正式评分，摄像头也只对沟通表达和应变能力做有上限的弱修正。」与「摄像头只对沟通表达、应变能力做有上限的弱修正。」

问题：引擎的 `A11_BODY_SCORE` 默认值为 1，弱修正已经开启，只修沟通表达与应变，幅度上限为 ±0.30 与 ±0.20。6.5.5 的「即使接入」是旧口径。

建议：统一为「引擎链路默认开启，只修正沟通表达与应变能力，幅度上限为 ±0.30 与 ±0.20；原链路报告只展示，不重算五维」。

### B6 内存预检门槛的两个数字

位置：6.5.2、7.4.2。

原文：「代码中的内存预检门槛是 1200MB。」

问题：引擎默认是 1200MB，`start.py` 在演示环境注入 800MB，避免整机可用内存不够导致转写直接 503。

建议：补一句「演示环境由启动脚本注入 800MB」。

### B7 题库「逐题人工精修」的量级存疑

位置：5.2.2。

原文：「团队对每道题的答案进行了多轮人工精修……平均长度从最初的几十字提升到 570 至 760 字。」

问题：5012 题逐题人工精修的工作量与团队规模不匹配，评委可能追问「几个人、多长时间、怎么质检」。当前题库的结构化字段更可能是流程生成加抽检。

建议：改为「结构化字段由流程生成，团队按比例抽检并修正」，并给出抽检比例。如果确实做过全量人工，准备好人月数。

### B8 数据来源的版权与合规口径

位置：5.1.1。

原文：「题库素材来自 GitHub 开源仓库……以及从大厂真实面试流程中整理的题目。」

问题：「大厂真实面试流程」容易被理解为非公开内部材料，涉及保密协议。GitHub 仓库也有许可证差异。

建议：改为「公开面经与开源仓库中的常见问法，不包含任何非公开面试材料」，并注明只使用 MIT、Apache 等允许再使用的仓库内容。这一点可以留作评委提问，提前准备答案。

12.2.2 已经写「成长档案、专项练习、参考答案与考点讲解等功能已实现接口层闭环，但前端界面尚未接入」。这句与当前状态一致，保留即可。注意把其中的「参考答案」按 A4 的口径改掉。

## 六、修改优先级

按答辩风险排序：
