## 第 1 章　团队分工

### 1.1 团队构成与分工原则

团队共 5 人，采用「技术分工 + 文档共建」的协作模式，按技术链路一人负责一段，从题库建设、算法开发、后端服务到前端界面，每一段都有明确的所有者。分工同时落实到目录归属：仓库中每个目录只对应一位负责人，模块内部如何实现由负责人决定，跨模块只通过接口文档约定的请求与响应格式对接。这样并行开发时不必互相等待，联调时也有据可查。后端开发 A 另承担技术负责人职责，包括接口文档维护与联调排期；项目文档的撰写与整合由 AI 评估与报告生成岗统筹，其他成员提供各自模块的素材。

### 1.2 各岗位职责与产出

#### 后端开发 A：主后端与面试状态机

主后端是整个系统的中间层：对前端提供统一的接口契约与鉴权体系，对内部编排 AI 对话与评估层、知识库检索两类服务，并把它们组织成完整的业务闭环。注册、选岗、多轮面试、五维评估报告、能力成长追踪，每个环节都经过这一层。

**数据基座与流程编排。** 落库 8 张业务表，覆盖用户、简历、岗位、题库、面试、问答记录、评估报告与报告分享。题型、难度、面试阶段等枚举值收敛到唯一定义处，词表调整后查询接口与导入脚本自动跟随。面试生命周期由表驱动状态机管理，只有 `idle → in_progress → finished` 两条合法转移，非法转换一律返回 409 冲突。一轮完整面试为「1 道开场题 + 6 轮动态追问」，持久化采用出题即落库、作答再回填的方式，面试在任意环节中断后都能恢复。

**集成与高可用。** 出题能力组织为五级数据源链：题库策略 → 语义检索 → 外部服务 → 大模型直连 → 内置兜底，任一级失败自动降至下一级。等待上限由分档超时预算约束（知识库检索 60 秒、评估 30 秒、通用调用 15 秒），依据各服务的实测耗时设定，其中知识库检索因含精排环节，单次实测 20 到 30 秒。外部服务返回的评分须齐全且落在合法区间，否则整体回退，异常数据不写入报告。内置兜底不依赖任何外部服务，是流程的最终保障。

**对话层接入与链路隔离。** 主后端在保留原有七轮对话流程的同时，接入独立运行的 AI 对话与评估层（10 题制，3/5/2 阶段），两条线路在创建面试时定死并写入会话记录，整场只读、中途不切换，避免半场换口径导致事后无从分辨。引擎未就绪时返回 503 而不是静默回落。引擎的会话保存在内存中，重启即丢，适配器对这类失效单独识别并收尾本场，避免产生无法作答也无法结束的孤儿会话。

**工程化与交付。** 累计 180 项自动化测试用例，测试库与开发库隔离；配套面试流程仿真工具，在算法与数据每次迭代后量化验证效果。一键启动脚本按顺序拉起知识库检索、评估服务、演示前端与主服务四个进程，就绪后打印本机与局域网访问指引，退出时统一回收。仓库同时推送到 GitHub 与 Gitee 两个远程，成员克隆任一个即可开发。

主要产出：`backend/app/`（接口层、业务层、适配层、数据层）、`backend/scripts/`（题库导入与流程仿真）、`backend/tests/`（180 项用例）、`backend/start.bat` + `start.py`（一键启动）、演示前端 `frontend_test/`（正式前端交付前的演示入口），以及接口文档、数据库设计文档、部署文档与各成员对接文档。

#### AI 对话层与面试官人格

该岗位负责面试过程中的对话决策与面试官形象的呈现：出一道什么题、考生的回答该不该追问、追问到什么深度、何时换题收尾，以及面试官以什么人格与节奏推进整场对话。

**面试官算法。** 出题以题库为唯一数据源，追问以锚点驱动：从对话历史尾部向前找最近一条题库原题（题干精确匹配），确定当前追问的是哪道题。锚点后已追问的次数决定层级：未追问取 L1，追问一次取 L2，两次取 L3，三次以上换新题。考生完全答不出时（识别为「露怯」：答案不足 20 字，或出现「不知道」「没接触过」等 12 个短语），追问改为降级引导，用该题的降级话术把考生拉回可回答的层面。第 6、7 轮强制换新题并偏向行为素质类题目，保证面试收尾完整；连续露怯的考生在换题时跳过深度压轴题。开场题不做锚点追问，避免挤占核心考察阶段的时间。

**V5 换代中的三处重写。** 题库换代到 V5 后，数据结构与 V4 差异很大，算法的三处实现随之重写。其一，追问素材从 V4 的单一自由文本字段改为 V5 的四个独立字段，原先 119 行的正则兼容层全部作废，改为直读字段；V5 的 L3 字段有三成题首行是元信息，取「最后一个追问行」的规则天然跳过。其二，L1 触发从关键词匹配改为语义分流：V5 的触发条件全部是描述式，关键词匹配实测 0/5012 命中，直接后果是「答得好的考生追问链根本不启动，面试退化成连问 7 道互不相关的题」；改为统一语义分流后，追问链触达率从 66% 提升到 100%。其三，V5 取消了「收尾交流」阶段，原先按阶段取收尾题的做法取到空集，会让面试降级到内置兜底；改为按题型「行为素质题」选题，题池反而扩大。

**对话层服务。** 面试交互由独立运行的对话层服务承担（8005 端口）：面试官人格提示词、追问生成、语音转写与成长档案等能力集中在这一服务内，出题、追问与五维评分均由它完成，主后端只负责镜像落库与报告换算。服务经历三个版本迭代，端点数从 6 个扩展到 10 个：语音作答经转写后连同语速、停顿等读数参与对话与评分，知识库检索为出题提供避重与深挖素材；每场面试结束生成成长档案与考后复盘清单，支撑错题本、考点地图与历史成绩三个视图。

**效果验证。** 算法骨架在 V4 阶段经两轮审查与 2700 场模拟验证；每次迭代后按「5 岗位 × 400 场」重跑流程仿真，验收基线为内置兜底 0 次、收尾题 100% 出现。

主要产出：`backend/interviewer_new/question_bank.py`（算法本体）、该目录的 README（算法速览与新旧版差异说明）、对话层服务及其集成适配、出题算法的测试用例。

#### AI 评估与报告生成

该岗位负责「面试结果量化」：设计多维评估提示词，输入对话全文与岗位要求，输出五个维度的结构化分数（技术、逻辑、表达、应变、匹配），并生成综合评语、优点、待改进与改进建议，支撑报告页的雷达图与成长曲线。评估能力与出题、追问、检索整合在同一服务层内，共享一个进程，分数按岗位权重加权，权重表按岗位区分并受自动化测试校验。

**按题校准。** V5 之前，评估输入只有岗位代码与对话文本，模型不知道每道题的考察意图：同一段回答，在「这道题只要求说清概念」与「这道题要求讲透原理边界」两种情形下应得的分不同，原实现无法区分。V5 的每道题自带单题校准锚点与基础、进阶得分点，主后端按题干从题库精确匹配取素材后随请求传入，评估逻辑将素材作为对话文本的一部分注入，模型判分即有了逐题的参照标准。

**双模型核验。** 评分采用两条线合成：客观线由 Qwen 做事实核验，把考生回答抽成技术主张、把标准答案拆成原子断言，逐条判断支持、矛盾或证据不足；主观线由 DeepSeek 完成五维评价与判档。两条线按置信度感知权重合成最终分数，不采用固定比例加权，降低单一模型的偏差。

**表达指标的测量。** 语音作答的客观读数按可复现的口径计算：语速为去标点字数除以净说话分钟数，长停顿为相邻人声区间间隔超过 1500 毫秒，填充词按固定字面量匹配，音量稳定性取各 3 秒窗均方根的标准差与均值之比。停顿检测基于人声活动检测切出的语音块，而不是转写段落的时间间隔，后者实测恒为零、会漏检。这些指标以「表达客观测量」的证据段注入评分提示词，支撑沟通表达与应变能力两个维度，但不单独成为评估维度，也不改变既定权重。

**降级与兜底。** 原实现中模型调用失败时按「空答卷」生成最低档兜底报告，与考生实际作答量无关；增强版把问答记录与岗位传入兜底分支，按实际答题篇幅分档。另外修正了岗位文案缺失时提示词拼出空字段的问题：V5 新增的两个岗位在权重表中已注册、评分文案尚未补齐，原实现会拼出「核心考察点：」后接空串，现以通用文案兜底。不传单题素材时，输出与此前的版本逐字一致，有 6 个回归用例守护这条兼容线。

**文档统筹。** 除评估工作外，本岗位统筹项目文档的撰写与整合：汇总各成员提供的模块素材，统一体例与术语，形成《项目详细方案》等对外材料，并按接口变更同步文档。

主要产出：评估能力的实现（评分逻辑与各岗位的评分细则文案）、语音指标分析、项目文档的统筹整合。

#### 前端全栈开发

前端是考生直接接触的界面，采用 Vue 3 + Vite + TypeScript 实现，覆盖桌面端与移动端的响应式布局，共 14 个页面与 1 个设置组件，覆盖登录注册、选入页、岗位大厅、面试对话室、报告页、问答历史、分享页、个人中心、简历页、题库中心等场景。

**页面与功能。** 认证部分包含登录、注册（含学号与目标岗位）、退出与资料编辑、头像更换。主流程从选入页进入岗位大厅（岗位卡片由后端动态下发），岗位详情页展示技术栈与考察重点，面试对话室支持文本与语音两种作答方式：聊天气泡、打字动画、顶部轮次显示，桌面端附进度面板，支持主动结束与退出保存，未完成的面试再次进入时提示继续或重新开始。报告页包含综合总分、五维雷达图、按岗位筛选的成长曲线、综合评语与改进建议、学习计划、问答回溯与分享导出。其余页面为免登录分享页、问答历史页、个人中心、题库中心、简历模块与 404 页面。

**语音输入的两级设计。** 语音作答采用两级结构：浏览器本地 Vosk 识别配合 MediaRecorder 录音，提供「边说边出字」的实时预览；松开话筒后录音上传主后端的转写接口，以服务端转写文本为准，同时取回音频地址与语速、停顿等表达读数。这样分工的原因是两者的短板恰好互补：本地识别精度不足，也给不出评估所需的读数；服务端转写无法实时出字，接口不可用时整条语音链路会失效。转写失败时保留本地识别文本并弹出提示、不提交音频地址与读数，考生可手动修改文本后继续作答。

**可视化与播放。** 报告页的雷达图与成长曲线使用 ECharts 绘制，分享图片用 html2canvas 导出 PNG；语音播放与姿态分析分别接入语音合成与 MediaPipe 视觉能力。

**开发与对接方式。** 前端不直接访问对话层、评估与检索服务，所有请求统一走主后端；后端未就绪时通过开发开关用本地模拟数据独立开发，联调阶段切换为真实接口，切换只改一处配置。接口勘误（如把提交答案误当作流式接口、路径缺少 `/api/v1` 前缀、字段名与实际不符）经整理后形成权威版本，前端另交付一份 25 条接口对照表供后端逐条核对，核对结果为路径全部正确、6 处字段名修正，修正后完成全部联调。

**交付方式。** 构建产物（`npm run build` 输出）整体拷贝到 `backend/static/`，与主服务同端口挂载，无跨域配置，评委拿到项目后无需单独启动前端开发服务器。

主要产出：`frontend/` 工程目录、`backend/static/` 构建产物、功能清单与接口对照表两份交付文档。

#### 知识库构建与测试

**题库生产。** 题库由三类内容汇合而成：从 GitHub 上二十余个公开面试资料库（JavaGuide、advanced-java、CS-Notes、system-design-primer 等）整理的基础题目，参考字节、阿里、百度等大厂技术面试与追问方式的真题语料，以及团队按岗位技术栈和题型缺口补充的原创题。原始内容经提取、清洗、分类与字段统一后形成主库：五个岗位共 5012 道结构化题目（后端开发 2146、前端开发 734、测试开发 667、算法工程师 655、系统设计工程师 810），每题 18 个字段，包含基础与进阶得分点、L1 至 L3 三级追问、降级策略、单题校准锚点、关联知识点等；题型、难度与面试阶段按统一词表取值（四类题型、三档难度、三个阶段），题目、得分点、追问与知识点共用岗位标识，保证出题、检索、图谱与评分模块稳定读取。题库是出题、追问与评估三段能力的唯一数据源：改 JSON 后跑一条导入命令即可生效，全程不动后端代码。导入流水线支持预检（只看统计不落库）、按岗位与题目标识幂等重跑、重建表结构前自动备份。

**质量治理。** 建库完成后另做了一轮系统的数据治理：以 JSON Schema 校验必填字段、字段类型与枚举值，按岗位校验题量，检查检索索引是否缺失原题、追问内容与主库是否一致，过滤得分点不足的低质量题，检测模板化的降级话术与错误归因表达；改动前自动备份，并保持题目标识与字段名不变。这轮治理重写了 L1 追问 3230 条、L2 追问 2682 条、L3 追问 2915 条、降级策略 5012 条。题库本身不记录每道题的来源链接，可核查的是结构化程度与治理流程。

**向量检索。** 同一份题库数据经向量化后生成 74011 条检索条目，由独立检索服务（端口 8003）提供两段式检索：语义召回后接交叉编码器精排，支持选题与展开两种模式，并通过 HTTP 接口供对话层调用，实现语义检索与追问素材的获取。

**全流程测试。** 测试覆盖数据、算法、接口、页面、异常与降级五个层面。数据侧校验题量与字段合法性、三级追问的可解析性、题库与检索条目及知识图谱三方数据的一致性；流程侧覆盖注册登录、选岗、出题与追问、断点续答、报告生成、分享与权限边界；异常侧覆盖在线转写失败回退本地模型、大模型超时返回降级报告、返回非 JSON 或分数越界时的兜底、知识库不可用时退化为无检索模式等分支。完整冒烟测试 2824 项全部通过、失败 0 项，另有 169 项单元与接口测试、覆盖 5 个岗位的 2000 场流程模拟与 150 条固定回答的回归验证。

**过程中的典型问题。** 治理中发现知识图谱在 Java 题库中有 444 题知识点为空、939 题与主库不一致，最终确定「主库为真值源、图谱只做过滤，不参与排序与评分」的口径；旧版追问存在「你刚才提到」这类错误归因与模板化话术，已按题批量重写。检索服务的超时预算最初按通用档设为 5 秒，与实际 20 到 30 秒的耗时不匹配，导致每次检索都被误判为服务不可用，后调整为 60 秒并增加健康探测缓存。向量库一度无法加载，排查确认 chromadb 打不开含非 ASCII 字符的绝对路径，实测 10/10 失败，用中文路径构建出的库表面正常、实际缺少索引文件；项目因此重跑过一次 6 小时的全量重建，此后向量库目录固定为纯 ASCII 名并写入文档。题库换代时的受控词表变更（如「技术知识」变为「技术知识题」）若照旧值书写会导致整条记录被跳过，导入流水线以预检模式加统计汇总兜底。

主要产出：`backend/rag/数据/*-v5.json`（5012 题五个文件）、`backend/rag/vector_db/`（74011 条向量条目）、RAG 检索接口与题库维护手册、质量治理与测试记录。

### 1.3 协作机制

**接口契约先行。** 模块间只通过接口文档对接。接口文档是唯一权威，字段有任何变化由后端开发 A 更新文档并同步通知，各岗位据此调整实现。前端的页面需求、AI 能力的调用契约（请求参数、返回结构、错误码）都在开工前写成文档交付。前端不直接访问对话层、评估与检索服务，所有请求经主后端转发；AI 服务对外只暴露必要的结构化字段与评分结果，模型密钥、完整得分点与内部提示词不出服务边界。

**目录归属与端口约定。** 每个目录只对应一位负责人，跨岗位修改需先沟通。端口分配全局固定，避免本地开发互相冲突。

| 8005 | AI 对话与评估层 | AI 对话层与面试官人格 |

**例会与沟通。** 团队以线下会议与腾讯会议作为正式讨论场合，日常沟通通过即时通讯工具随时进行。关键节点组织全体会议：9 月中旬确定核心功能范围与分工方向，下旬讨论交互设计、题库分类与评价方式等实现细节；9 月下旬的联调会确认首次通过虚拟网络打通前后端与数据库，从注册登录到面试、出报告与历史记录的完整流程走通。

**版本管理与交付。** 项目采用 Git 进行版本管理，各成员在独立分支开发，通过合并请求完成代码集成；仓库配置 GitHub 与 Gitee 两个远程，内容保持一致，成员就近克隆，提交信息统一使用中文加前缀（feat / fix / docs / test）。密钥与运行数据不入库：接口密钥只存本地环境文件，向量库、模型权重、数据库文件均通过忽略规则排除，模型在首次启动时自动下载。项目最终以一键启动脚本交付，单条命令拉起全部服务。

## 第 2 章　项目实施过程

### 2.1 实施路线与阶段划分

项目按「需求与方案 → 核心开发 → 集成增强 → 测试交付」四个阶段推进。前两个阶段自上而下打地基与主流程，后两个阶段并行推进：集成增强期间测试与文档同步起步，直到交付前收口。

[图 2-1：项目实施路线与各模块工作区间　配图：`figures/fig-2-1-项目实施甘特图.png`]

### 2.2 阶段一：需求分析与方案设计

**核心目标**：明确系统边界与技术路线，形成可执行的分工与开发计划。

**关键任务**：分析大学生求职面试的实际痛点（求职失败主因调查中，简历、面试紧张、表达沟通三项均与面试环节直接相关），确定「模拟面试 + 五维评估 + 成长追踪」的产品形态，形成产品需求文档与功能需求清单；完成技术选型，主后端采用 Python FastAPI（异步）与 SQLAlchemy 2.0 异步 ORM，数据层默认 SQLite、零配置启动，界面层采用 Vue 3 + Vite，AI 能力组建为对话与评估层、知识库检索服务；设计五维评估体系（技术、逻辑、表达、应变、匹配）与各岗位权重表；划定目录归属、端口分配与协作规范，接口文档先行交付。

**交付物**：产品需求文档、功能需求清单、评估维度定义（各岗位五维权重表）、接口文档初稿、协作指南。

[图 2-2：需求分析依据——求职失败主因调查　配图：`figures/fig-1-2-求职失败主要原因.png`]

### 2.3 阶段二：核心功能开发

**核心目标**：跑通「创建面试 → 出题 → 作答 → 动态追问 → 结束 → 生成报告」完整闭环。

**关键任务**：后端基座先行，完成数据模型、鉴权体系、面试状态机、统一响应与错误码体系，并配套一键启动脚本与双远程仓库的协作配置；评估能力交付，实现五维评分与报告文本生成；题库升级与面试官算法落地，算法以原生模块形式接入出题数据源链，形成「题库策略 → 语义检索 → 外部服务 → 大模型直连 → 内置兜底」的五级结构；期间演示前端先行交付，作为正式前端完成前的演示与联调入口；项目中期完成一次大规模换代，题库从数百题扩充到 5012 题，面试官算法、检索服务与评估能力同步重做，全队在同一次迭代中对齐新数据结构。

**交付物**：可运行的主后端服务、评估能力、面试官算法模块、V5 题库与检索服务、演示前端、接口文档与各岗位对接文档。

### 2.4 阶段三：系统集成与能力增强

**核心目标**：在闭环之上扩展功能面与 AI 能力，形成练习、评估、提升的完整闭环。

**关键任务**：个人中心与报告分享上线，支持资料编辑、头像上传、按岗位筛选的历史与成长曲线、限时免登录分享链接；学习资源推荐与简历导入接入，简历解析结果可回填至面试上下文；AI 对话层服务分三个版本迭代，新增语音转写、成长档案、考后复盘、朗读与体态分析等能力，语音作答的语速、停顿等读数随作答回传参与报告生成；前端全栈开发进入集中实现期，后端按页面需求文档交付接口契约，并随功能上线分批增补（个人中心与报告分享、学习资源与简历），前端完成后交付 25 条接口对照表，双方逐条核对并修正字段差异。

**交付物**：个人中心与报告分享接口、简历与学习资源接口、对话层服务集成、语音能力、前端全部页面与联调记录。

### 2.5 阶段四：测试优化与成果交付

**核心目标**：验证质量、优化性能，完成全套成果材料的整理与提交。

**关键任务**：测试工作自核心功能完成即开始，与后续开发并行推进，最终形成 180 项自动化测试用例，覆盖鉴权、岗位、题库、面试流程、报告、分享、上传等模块，测试库与开发库隔离，全量运行约 10 秒；面试流程仿真在每次算法与数据迭代后重跑，以「5 岗位 × 400 场、兜底 0 次、收尾题 100% 出现」为验收基线；并发写入优化落地（写前日志模式与忙等超时配置），多场面试并发提交不锁库；前端构建产物拷入主服务静态目录，完成同端口部署；文档与材料方面，依次完成开发手册、新增代码清单、竞赛三册材料、详细方案章节稿与配套插图、前端联调指南，直至本文。

**交付物**：自动化测试套件、流程仿真数据、优化后的并发配置、前端构建产物、全套技术文档与竞赛提交材料。

### 2.6 风险与应对

**表 2-1　主要风险与应对措施**

| 风险 | 应对措施 |
| :--- | :--- |
| 外部服务（大模型、知识库）不可用或超时 | 五级数据源降级链，任一级失败自动落到下一级；内置兜底不依赖任何外部服务，流程不因外部依赖中断；超时预算按各服务实测耗时分档设定 |
| 题库换代导致算法与评估失效 | 换代后重跑全岗位流程仿真，以兜底次数与收尾题出现率为验收基线；受控词表集中定义，非法值直接报错而非静默返回空集 |
| 大模型调用成本随使用量增长 | 优化提示词长度减少无效消耗；对高频场景建立缓存；在精度允许范围内以更小的模型处理简单场景 |
| 语音识别在真人场景下的准确率不确定 | 提供转写文本手动校对，降低识别误差的影响；持续优化语音活动检测参数与热词表 |
| 数据隐私与合规 | 录音只在内存与临时文件中存在、转写完成后即删除，音频与转写原文不进数据库、不进日志；用户可随时删除自己的面试记录 |
| 向量库大文件无法入库 | 向量库、模型权重与检索数据通过忽略规则排除；模型首次启动自动下载，网络受限时支持镜像源切换 |
| 运行环境差异（终端编码、路径字符集）导致服务起不来 | 启动脚本以纯 ASCII 引导加 Python 主逻辑实现，规避终端编码差异；向量库目录固定纯 ASCII 名，避免路径字符集导致索引文件缺失 |
| 对话层服务会话存储在内存，重启即丢 | 演示期间不重启服务；适配器识别会话失效后收尾本场并提示重新开始，避免产生孤儿会话 |
| 前端交付节点靠后，影响整体演示 | 需求与接口文档先行交付，演示前端作为过渡入口；联调阶段以接口对照表逐条核对，降低返工 |
